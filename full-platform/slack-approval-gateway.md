# Slack Approval Gateway

## What problem this solves

Two human-approval gates exist in the delivery pipeline:

1. **The GitOps PR gate** -- every change to any cluster is a commit to `microservice-app-gitops`'s `main`, which requires one approving review (branch protection, `required_approving_review_count: 1`). This includes the automated `promote/*` PRs `promote.yml` opens.
2. **The prod-environment gate** -- each service repo's `ci.yml` has a `gate-prod` job targeting a GitHub Environment named `prod`, configured with `required_reviewers` (Juanmadiaz45, EstebanGZam, Tiago0507). It is live: org variables `ENABLE_LEGACY_DEV_PROMOTION`/`ENABLE_LEGACY_SEMANTIC_RELEASE` are both `true`.

Gate 2 was silent -- a run just sits paused with no notification anywhere until someone happens to check GitHub. `microservice-app-slack-approval-gateway` (two AWS Lambda functions behind an API Gateway HTTP API) fixes both:

- Gate 1 gets a Slack message with **Approve** / **Request changes** buttons -- clicking one calls GitHub's API for real (submits the review, merges on approve).
- Gate 2 gets a Slack **notification** (technical + non-technical summary, a direct link to GitHub's "Review deployments" screen) -- no button. GitHub's classic `required_reviewers` cannot be satisfied by a GitHub App token on behalf of a listed human (only Users/Teams can be listed reviewers; confirmed against GitHub's REST API docs), and the team chose to keep that approval exactly as it is today rather than replace it with a custom deployment-protection-rule app. Slack tells you it is waiting; you still approve it in GitHub.

Both messages carry a **technical** summary (the PR's own already-reviewed body sections, or deterministic job/run metadata -- verbatim, never re-derived) and a **non-technical** rephrasing generated by the Gemini API, explicitly prompted to use only the facts given and never add anything unstated -- so a non-engineering stakeholder (a manager, a client) can understand what is about to happen without needing the technical detail.

## Why two new GitHub Apps, not one, and not one of the existing two

`microtodosuite-release` and `microtodosuite-gitops-promoter` (see `github-app-authentication.md`) exist to *act* within a specific, narrow scope (mint a release, open a promotion PR). Folding this system into either would widen its blast radius for no reason.

A single new App would not actually preserve least privilege either: GitHub Apps declare **one** permission set that applies uniformly to every repository the App is installed on -- there is no way to grant write access on one installed repository and read-only on another within the same App. Since gate 1 needs write access on `microservice-app-gitops` and gate 2 only ever needs to receive a webhook from the five service repos, one App covering both would carry unused write permission on all five service repos. So this is **two** Apps instead:

| App | Backs | Installed on | Permission | Webhook subscription |
| --- | --- | --- | --- | --- |
| `microtodosuite-gitops-slack-approver` | `github-webhook-handler` (reads) + `slack-interaction-handler` (acts) | `microservice-app-gitops` only | Pull requests: write, Contents: write | `pull_request` |
| `microtodosuite-prod-gate-notifier` | `github-webhook-handler` (reads only) | The five service repos | Actions: read-only | `workflow_job` |

Both Apps' webhook deliveries point at the same API Gateway route (`{api_base_url}/github/webhook`) -- `github-webhook-handler` already dispatches on event type and repository name, not on which App sent the delivery. Only `microtodosuite-gitops-slack-approver`'s installation token is ever used to call GitHub back (to approve and merge); `microtodosuite-prod-gate-notifier` never makes an authenticated API call at all, so **it has no private key stored anywhere** -- it only needs to exist, be installed, and share the same webhook secret.

Org secrets (selected-repository visibility is not used here -- see below, these are not GitHub Actions secrets at all): `microtodosuite-gitops-slack-approver`'s id/key live in **AWS Secrets Manager**, not as repository or organization Actions secrets, because nothing in this flow runs as a GitHub Action -- the Lambdas fetch them directly at invocation time.

## Where the credentials actually live

Unlike the release/promoter Apps (consumed by GitHub Actions, so their credentials are GitHub Actions secrets), `microtodosuite-gitops-slack-approver`'s credentials are consumed by a Lambda function outside GitHub entirely. They live in AWS Secrets Manager, provisioned by the Terraform module in `microservice-app-ops` (`aws/shared/slack-approval-gateway/`), and are fetched by the Lambda at runtime via the AWS SDK -- never logged, never written to disk, cached only in the warm execution environment's memory. The same value-blind discipline `scripts/managed/bootstrap-sonarqube.sh` (spec 009 T103) applies here: a credential is read once, used once, never echoed. `microtodosuite-prod-gate-notifier` has no key to store at all.

| Secret | Used by |
| --- | --- |
| `SLACK_APPROVER_APP_KEY` (`microtodosuite-gitops-slack-approver`'s private key) | Both Lambdas -- mint an installation token |
| `SLACK_SIGNING_SECRET` | `slack-interaction-handler` -- verifies a click really came from Slack |
| `SLACK_BOT_TOKEN` | Both Lambdas -- post/update Slack messages |
| `GITHUB_WEBHOOK_SECRET` | `github-webhook-handler` -- verifies a webhook really came from GitHub. The same value is configured on both Apps' webhook settings. |
| `GEMINI_API_KEY` | Both Lambdas -- the non-technical rephrasing |

The App id itself (`SLACK_APPROVER_APP_ID`, `microtodosuite-gitops-slack-approver`'s id) is not sensitive -- a GitHub App id is public information -- so it is passed straight through as a plain Lambda environment variable rather than a Secrets Manager entry. `microservice-app-ops`'s own delivery contract (`tests/contract/aws-dev-foundation.sh`) forbids an ordinary, state-persisted Secrets Manager value anywhere in `aws/`, precisely so no one has to judge case-by-case whether a given value is "sensitive enough" to earn the write-only treatment.

## Private-key handling: mode 0600, then gone

Identical discipline to `github-app-authentication.md`, and only relevant to `microtodosuite-gitops-slack-approver`: download the App's private key once, `chmod 600` it immediately, upload it straight into AWS Secrets Manager from that file (`aws secretsmanager put-secret-value --secret-id ... --secret-string file://key.pem`, or the Terraform-managed equivalent), then delete the local file the moment the secret is confirmed set.

## Rotation

Same zero-downtime pattern as the other Apps: generate a new private key in `microtodosuite-gitops-slack-approver`'s settings (the old one keeps working), upload it as the new secret value, confirm one real webhook delivery authenticates with it, then delete the old key from the App's settings. `microtodosuite-prod-gate-notifier` has nothing to rotate; only its shared webhook secret needs to change, on the same schedule as `GITHUB_WEBHOOK_SECRET`, updated identically on both Apps.

## The authorization boundary

`config/authorized-approvers.json` in `microservice-app-slack-approval-gateway` maps a Slack user ID to a GitHub login. It intentionally lists exactly the three logins already configured as `required_reviewers` on every service repo's `prod` Environment -- this system does not grant anyone new authority, it only lets an already-authorized reviewer act through Slack instead of the GitHub UI for gate 1. Any Slack click from a user not on that list is refused, logged, and the click's own `response_url` is used to tell that person so -- it is never silently ignored, and it never reaches GitHub.

## What this does not do

- Does not replace or touch `required_reviewers` on any `prod` Environment -- gate 2 stays exactly as it is; this system only adds the missing notification.
- Does not let anyone approve gate 2 from Slack -- that would require each listed reviewer to complete a one-time GitHub OAuth user-token grant so the App could act with their own identity rather than an installation token (a real option for a future iteration, not built here).
- Does not run as a GitHub Action or inside the EKS cluster -- it is two standalone Lambda functions, chosen specifically because the economical cluster has never exposed anything to the internet (no Ingress exists anywhere in `microservice-app-gitops`; spec 004 User Story 4 deliberately limits access to `kubectl port-forward`), and building a first Ingress+ALB+ACM+DNS just for this would be a larger project than the gateway itself.
