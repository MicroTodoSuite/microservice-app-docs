# Pull Request and Task Tracking Conventions

**Applies to**: every repository in the MicroTodoSuite organization, and to every
contributor — people and AI agents alike.

**Status**: binding. Constitution principle 13 makes these rules non-negotiable;
this document is the detail that principle points at.

These conventions codify what the project already does well in places and did
inconsistently elsewhere. They exist because two concrete failures happened:
pull requests arrived in whatever shape their author felt like, and work was
delivered without its task register ever being updated — spec 007 sat at 0/27
for weeks while all of its artifacts were already merged.

---

## 1. Branches

One branch, one concern, short-lived. Delete it on merge.

```
<type>/<short-kebab-summary>
```

`<type>` is one of:

| Type | Use |
| --- | --- |
| `feat` | New behavior |
| `fix` | Corrected behavior |
| `test` | Tests committed ahead of their implementation |
| `docs` | Documentation and specification text |
| `chore` | Dependencies, tooling, housekeeping |
| `ci` | Workflow and pipeline changes |
| `promote` | Digest promotion in `microservice-app-gitops` |

Examples from this repository's history that follow the rule:
`feat/full-profile-secrets-and-evidence`, `fix/bump-image-digest-only`,
`docs/plan-reconciliation`.

Personal-name branches (`esteban/...`) and bare-word branches (`env/...`,
`agent/...`) are retired. They say who, not what.

## 2. Commits

[Conventional Commits](https://www.conventionalcommits.org/) with a scope.
`semantic-release` depends on this, so it is not cosmetic — the type determines
the released version.

```
<type>(<scope>): <imperative summary, lower case, no trailing period>

<body: why, not what. Wrap at 80 columns.>
```

**Scope** is the user story when the work belongs to one (`us1`, `us2`, `us3`),
otherwise the area (`aws`, `tests`, `observability`, `evidence`, `promotion`,
`deps`, `specs`).

**Spec-Driven Development pairs.** When a change follows the test-first cycle,
it lands as two commits in this order, and the first one must fail:

```
test(us3): specify the auth-api operational contract
feat(us3): implement the auth-api operational contract
```

Do not squash that pair. The failing-test commit is the evidence that the cycle
was followed; collapsing it destroys the proof.

**The body explains why.** A summary line that restates the diff is wasted. If
the change fixes a real defect, name the defect and its consequence. If a claim
in an earlier commit turns out to be wrong, correct it in a later commit body
rather than leaving the record wrong.

`chore(release): X.Y.Z [skip ci]` commits are generated by `semantic-release`.
Never hand-write one.

## 3. Language

**Everything is in English.** Branch names, commit messages and bodies,
pull-request titles and bodies, review comments, code comments, documentation,
and specification text. No exceptions and no bilingual sections.

`AGENTS.md` has always said "write all project artifacts in English"; this
states plainly that a pull request is one. A pull-request body is a project
artifact: reviewers read it, it is the record of why a change was made, and on a
squash merge it can become the commit message itself.

Conversation that never lands in a repository is not restricted. Discussing a
change in another language is fine; writing it into the repository is not.

**Changing this rule takes a recorded decision**, not a remark in conversation.
It was briefly amended to require bilingual bodies on 2026-08-30 and reverted
the same day, because the amendment was made from an ambiguous message rather
than from a decision anyone had actually taken. Anyone — person or agent — who
believes the rule should change opens a pull request against this document and
says why.

## 4. Pull request title

The same string as the primary commit. No PR numbers, no "WIP", no emoji.

## 5. Pull request body

Use `.github/pull_request_template.md`, present in every repository. Every
section is required; delete none of them. Write "N/A" plus one clause of reason
where a section genuinely does not apply.

| Section | What it must contain |
| --- | --- |
| **What changes** | The behavior difference, not a file list. GitHub already shows the file list. |
| **Why** | The problem this solves. For a defect: what breaks today, and what the user or operator experiences. |
| **Tasks** | The task IDs this PR advances, each with the register it lives in — `gitops specs/007-advanced-testing T014`. See §7. |
| **How it is verified** | The exact commands run and their result. For a guard, the mutation result. For infrastructure, the plan summary. |
| **Risk and rollback** | What could break and how to undo it. For GitOps, this is normally "revert the commit"; say so rather than leaving it blank. |
| **What this PR does not do** | Scope you deliberately left out, so a reviewer does not look for it. |

**Evidence is quoted, not described.** "Tests pass" is not verification; the
command and its output tail is. Where output is long, quote the decisive lines.

**A PR body must never claim something the author has not observed.** If CI is
red, say what is red and why. If a step was skipped, say it was skipped.

## 6. Review and merge

| Repository | Approvals required | Notes |
| --- | --- | --- |
| `microservice-app-gitops` | 1 | `main` is protected with `enforce_admins: true` |
| every other repository | 0 by policy | Review is still expected for anything beyond a trivial fix |

Rules that hold everywhere:

- **Never merge with `--admin`, and never force-push to `main`.** Spec 009 T160
  audits for exactly this. If a protection rule blocks a merge, the rule is
  working; get the approval.
- **Never disable a branch protection rule to land your own work.** Removing the
  review requirement to merge unreviewed changes makes the audit trail record a
  review that did not happen.
- **No one approves their own pull request.** GitHub enforces this; do not route
  around it with a second account or by weakening the rule.
- **An AI agent may open, describe, and update a pull request. It may never
  approve one, and may never author an acceptance or approval artifact.** Only a
  named human unlocks a gate.
- Squash-merge and delete the branch. The PR body survives as the merge commit
  message, which is why it has to be worth reading.
- **A check that this change turned red blocks the merge.** A check that was
  already failing on `main` for an unrelated reason does not — merging a
  documentation change into a repository whose image scan was red yesterday
  neither causes nor hides anything. State the pre-existing failure in the body
  so the reviewer can see you knew about it. What is never acceptable is
  merging past a check *your own change* broke.
- A security finding is a team decision recorded in its own reviewed change,
  never a suppression slipped into a feature branch.

## 7. Task tracking — the traceability rule

This is the section that exists because delivery and its record drifted apart.

**Every unit of work is traceable to a task, and every completed task is marked
in the same pull request that completed it.**

Concretely:

1. **Name the tasks in the PR body.** Every PR states the task IDs it advances,
   qualified by repository and spec: `gitops specs/009-full-platform-rollout
   T045`. A reviewer must never have to guess what a change was for.

2. **The register update ships with the work.** `tasks.md` is edited in the same
   PR that delivers the task. A follow-up bookkeeping PR is not acceptable —
   that is precisely the gap that let spec 007 read 0/27 while it was 21/27.

3. **Tick only against a located artifact.** A task is marked `[X]` when its
   named file, resource, or evidence has been found and inspected. Never tick
   from a summary, a green check, a rendered manifest, a passing exit code, or
   someone's recollection.

4. **Partial delivery is annotated, never ticked.** If a task asks for three
   things and two exist, it stays `[ ]` and the PR body says which part landed.
   Spec 007 T011 and T012 are the worked example: one pact of three shipped.

5. **Work with no task gets a task first.** If you are about to do something the
   registers do not cover, add the task — or, for a genuinely trivial fix,
   record in the PR body that no register applies and why. "No task" is a
   statement someone must be able to disagree with, not a silence.

6. **A verification task needs an observed run.** Tasks whose text says
   "observe", "verify", "prove", or "record" are not satisfied by the code
   existing. They need the run, and the evidence retained where the task says.

7. **Never mark a task complete on someone else's behalf**, and never author the
   acceptance artifact that closes a user story. That is a maintainer's
   signature.

8. **When a register and reality disagree, reconcile — do not quietly edit one
   side.** If a specification pins a version that was never shipped, or names an
   artifact that does not exist, that is a decision for the maintainer. Record
   the discrepancy; do not resolve it by rewriting whichever side is more
   convenient. `full-platform/plan-reconciliation.md` is the worked example.

## 8. Cross-repository changes

A change spanning repositories lands as one PR per repository, each naming the
others in its body, merged in dependency order. Do not mix unrelated
repositories or delivery stages in one pull request.

The stage and PR order for the full-platform rollout is in
`full-platform/rollout-index.md`.

## 9. For AI agents specifically

Everything above binds agents. These additions are agent-specific because they
are failure modes automation has and people mostly do not:

- **Follow this document when opening any pull request in any MicroTodoSuite
  repository.** It is not advisory.
- **Report outcomes faithfully.** If the work is partially done, say which part.
  If a test was not run, say it was not run. A PR body that overstates what was
  verified is worse than no PR body.
- **Correct your own record.** If a claim in an earlier commit or PR body turns
  out to be wrong, amend it or say so plainly in the next one. A commit message
  asserting a CVE was fixed when it was not is a defect in the audit trail.
- **Do not work around a blocked action.** A refused permission, a protected
  branch, or a failing gate is a signal to stop and report, not an obstacle to
  route around.
- **Prefer the smallest reviewable change.** A PR a human cannot review is not
  a contribution.
